# ЭХО: офлайн-доступ и безопасные обновления

## Как работает офлайн-доступ

- Service Worker отдельно кеширует оболочку приложения, стили, модули, заставку, каталог и манифест.
- Тексты глав хранятся в отдельном версионированном кеше.
- После открытия книги менеджер загружает недостающие главы в фоне, по две одновременно.
- Каждая глава проверяется по SHA-256 до сохранения в версионированный кеш.
- Если загрузка прервана, уже сохранённые файлы остаются на месте. При следующем запуске менеджер проверяет кеш и продолжает с недостающих файлов.
- Пока первичная загрузка не завершена, офлайн-доступны только уже загруженные главы.

## Как работают обновления контента

- При запуске приложение получает свежие `chapters.json` и `chapters-manifest.json` напрямую из сети.
- Если версия изменилась, создаётся отдельный staging-кеш.
- Неизменённые главы копируются из активного кеша по совпадающей SHA-256. Из сети скачиваются только новые или изменённые файлы.
- До полной проверки всех файлов активная версия остаётся нетронутой.
- После полной готовности staging-версия помечается как ожидающая.
- Ожидающая версия активируется при следующем полноценном запуске. Текущее чтение не переключается посреди сессии.
- Предыдущий кеш сохраняется как страховка; автоматического удаления старой версии контента нет.

## Как подготовить обновление текста

1. Обновить нужные отдельные файлы в `data/chapters/`.
2. Обновить `data/chapters.json`, если меняются названия, номера, ID, состав или пути глав.
3. Выполнить в корне проекта команду `node tools/build-content-manifest.mjs`.
4. Убедиться, что вместе с изменениями опубликован `data/chapters-manifest.json`.

Постоянный ID главы не менять при простом изменении её номера или позиции. Изменение файла главы обязательно отражается новой контрольной суммой.

## Обновления оболочки приложения

Когда меняются `index.html`, CSS или JavaScript-модули, нужно задать одинаковый новый `BUILD_ID` вверху `sw.js` и `content` у meta-тега `echo-build` в `index.html`. Новый Service Worker сначала полностью кеширует новую оболочку. Если установка кеша не удалась, предыдущая активная версия продолжает работать. После успешной установки worker вызывает `skipWaiting()`, а при активации — `clients.claim()`. Это устраняет ожидание закрытия вкладок.

Приложение проверяет обновление при запуске, возвращении из фона, восстановлении соединения и каждые 5 минут в активной вкладке. Через сообщение `ECHO_GET_BUILD` страница сравнивает свою версию с активным контроллером. Если версия отличается, приложение перезагружается только на заставке или в оглавлении, восстанавливая текущий экран. Во время чтения обновление интерфейса отложено до выхода в оглавление или следующего запуска. Прогресс, настройки и кеши глав не очищаются. При первом переходе со старой версии без этого механизма уже открытая вкладка может потребовать одну обычную перезагрузку. Сеть и публикация должны быть доступны для получения новой оболочки.

Кеширование оболочки остаётся согласованным: не заменяем отдельные CSS и JS сетевыми ответами посреди сессии. Обновление текста продолжает работать по отдельной схеме staging-кеша.

## Локальный сервер Windows

`start-server.ps1` включает MIME-тип `application/manifest+json` для `manifest.webmanifest`. Запускать проект через `start.bat`, а не двойным щелчком по `index.html`.
